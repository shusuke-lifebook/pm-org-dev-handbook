# PM／PMO 経験者用教科書

## はじめに

この教科書は、システム開発、業務運用、チームリーダー、PM補佐、PMO補佐などの経験を持つ人が、PMまたはPMOとして担当範囲を広げるための教材である。

初歩的な用語の暗記ではなく、複雑な状況での判断、複数の制約の調整、経営層への説明、組織横断の改善を主な学習対象とする。経験者であっても、所属組織や案件の進め方が変われば、前提や判断基準を確認し直す必要がある。

### この教科書の使い方

1. 各章の論点を読み、自分の経験と異なる点を確認する
2. 過去案件の判断を、目的・前提・選択肢・結果で再構成する
3. 現在の案件で適用できる改善を1つ選ぶ
4. 成果物または会議で適用し、関係者の反応と結果を記録する
5. 上位PM、PMO責任者、スポンサーと判断の質をレビューする

### PMとPMOの違い

経験者向けでは、PMとPMOの違いを「作業分担」ではなく「責任と意思決定の構造」として理解する。

PMは、担当プロジェクトの成果と意思決定に責任を持つ。PMOは、プロジェクトまたはポートフォリオ全体の可視性、標準、ガバナンス、意思決定品質を高める。強いPMOは、PMの判断を奪うのではなく、判断に必要な情報と選択肢を整える。

PMにも、単独案件の運営だけでなく、組織の投資判断や人材育成に影響を与える視点が必要である。PMOにも、報告資料を作るだけでなく、事業価値と現場の実行可能性を結び付ける視点が必要である。

# 第1部 共通基礎

## 第1章 ITとシステム開発の基本

### 1.1 技術を意思決定に変換する

経験者に求められるのは、技術用語を知っていることではなく、技術的な事実をプロジェクト上の判断材料へ変換することである。

例えば「データベースの変更が必要」という説明だけでは、管理上の判断はできない。次のように変換する。

- 何を変更するか：データ項目と連携処理を変更する
- 影響するもの：既存画面、帳票、外部連携、移行処理
- 影響の大きさ：テスト範囲が増え、リリース候補日が3日後ろ倒しになる可能性
- 選択肢：今回対応、段階対応、代替運用
- 判断期限：設計凍結日の前営業日

### 1.2 アーキテクチャと非機能

PMは、機能要件だけでなく、性能、可用性、拡張性、セキュリティ、運用性、障害復旧性を計画へ組み込む。

技術的な選択にはトレードオフがある。短期の開発速度を優先すると、将来の保守性や運用負荷が増えることがある。PMOは、案件ごとの判断を横断的に比較できるよう、非機能要件と技術的負債を可視化する。

### 1.3 開発手法を状況に合わせる

ウォーターフォール、アジャイル、ハイブリッドの選択は、流行やチームの好みではなく、次の条件で判断する。

- 要求の安定度
- 技術的不確実性
- 規制・監査上の証跡要求
- 利用者からのフィードバック頻度
- リリースを分割できるか
- 意思決定者が継続的に参加できるか

ハイブリッドでは、どの領域を固定的に管理し、どの領域を反復的に進めるかを明確にする。方法論の名前より、計画、検査、適応の仕組みが機能しているかを評価する。

### 確認問題

1. 技術的な説明を、納期・コスト・品質の判断材料へ変換する例を作りなさい。
2. 非機能要件を後回しにした場合の経営上のリスクを挙げなさい。
3. ハイブリッド型を採用するとき、最初に合意すべき管理境界を説明しなさい。

## 第2章 プロジェクトの基本

### 2.1 価値と成果物を分ける

成熟したプロジェクト管理では、成果物の完成と事業価値の実現を分けて扱う。システムを納品しても、利用されなければ期待した価値は生まれない。

- 成果物：システム、手順書、移行データ、教育資料
- 成果：処理時間の短縮、入力率の向上、コスト削減
- 効果：利益、リスク低減、顧客満足、業務能力の向上

開始時に成果物だけでなく、価値を誰が、いつ、どの指標で確認するかを決める。

### 2.2 制約のトレードオフ

制約を一つだけ守ることは、全体最適とは限らない。納期を守るために品質検査を削れば、リリース後の障害コストが増える可能性がある。

制約変更の判断では、次を明示する。

- 何を守るべきか
- 何を変更できるか
- 変更による短期・長期の影響
- 誰が判断するか
- 判断を延期した場合の影響

### 2.3 プロジェクト憲章の高度化

経験者向けのプロジェクト憲章には、目的や範囲だけでなく、次を含める。

- 事業上の仮説
- 効果測定の責任者
- 意思決定権限とエスカレーション条件
- 主要な依存関係
- 許容できるリスク
- 変更の優先順位
- プロジェクト終了後の運用責任

### 確認問題

1. 成果物、成果、効果の違いを、自分の案件に当てはめなさい。
2. 納期を守るために品質を犠牲にする判断が許される条件を挙げなさい。
3. プロジェクト憲章に意思決定権限を記載するメリットを説明しなさい。

## 第3章 文書作成とコミュニケーション

### 3.1 意思決定文書

経験者の文書は、状況報告で終わらず、意思決定を支援する。意思決定文書では、推奨案だけでなく、採用しなかった選択肢と理由も残す。

基本構成：

1. 判断してほしいこと
2. 判断期限
3. 推奨案
4. 背景と目的
5. 事実と前提
6. 選択肢比較
7. 影響と残存リスク
8. 承認後の実行計画

### 3.2 不確実性を表現する

「確実」「問題ない」といった断定は、根拠と条件を伴わない限り危険である。予測には前提、確度、変動要因、更新条件を付ける。

- 事実：現時点で確認できていること
- 仮説：現時点で最も妥当と考える説明
- 予測：前提が維持された場合の見込み
- 判断：責任者が選択した方針

### 3.3 エグゼクティブコミュニケーション

経営層には、作業の詳細ではなく、事業目標への影響、選択肢、必要な判断、判断しない場合の影響を示す。詳細を削るのではなく、経営判断に必要な粒度へ変換する。

### 確認問題

1. 意思決定文書で採用しなかった案を記載する理由を説明しなさい。
2. 「問題ない」という報告を、条件付きの予測に書き換えなさい。
3. 経営層向け報告と開発チーム向け報告の違いを説明しなさい。

## 第4章 会議運営と合意形成

### 4.1 意思決定の設計

会議の成否は、発言量ではなく、意思決定の質と実行への接続で評価する。会議前に、決定権者、判断基準、必要な情報、許容できる未確定事項を整理する。

### 4.2 対立を構造化する

対立が起きた場合、意見の強さではなく、次の違いを確認する。

- 目的の違い
- 事実認識の違い
- リスク許容度の違い
- 評価指標の違い
- 権限や責任の違い
- 時間軸の違い

対立を解消することが目的ではない。前提と判断基準を明らかにし、決められる状態を作ることが目的である。

### 4.3 会議体のポートフォリオ

会議を個別に改善するだけでなく、会議体全体を見直す。情報共有会議、課題解決会議、意思決定会議、品質ゲートを混在させると、目的と参加者が曖昧になる。

### 確認問題

1. 対立を「目的の違い」と「事実認識の違い」に分ける方法を説明しなさい。
2. 意思決定会議に必要な情報を、事前に揃える方法を挙げなさい。
3. 会議体を廃止または統合する判断基準を作りなさい。

## 第5章 品質、リスク、課題

### 5.1 品質を経営課題として扱う

品質問題は、開発チームの問題だけではない。品質目標を下げる判断には、顧客、運用、法務、セキュリティ、財務への影響がある。

品質計画では、欠陥数だけでなく、利用者影響、障害復旧時間、データ整合性、監査証跡など、プロジェクトの目的に応じた指標を設定する。

### 5.2 リスクポートフォリオ

個別案件のリスクを並べるだけでは、共通原因や連鎖影響が見えない。PMOは、案件横断で次を確認する。

- 同じ技術やベンダーに依存しているか
- 同じ要員を取り合っていないか
- 同じ時期にリリースが集中していないか
- ある案件の遅延が他案件へ波及するか
- 共通の規制、セキュリティ、運用リスクがあるか

### 5.3 課題の意思決定化

課題一覧を更新するだけでは、課題管理にならない。重要な課題は、判断が必要な論点として整理し、期限、判断者、選択肢、推奨案を明確にする。

### 確認問題

1. 品質を下げる判断で確認すべき関係者を挙げなさい。
2. 案件横断でリスクを見るメリットを説明しなさい。
3. 課題一覧を意思決定一覧へ変換する方法を説明しなさい。

## 第6章 数値と表計算

### 6.1 指標の限界を理解する

数値は事実の一部を表すが、実態そのものではない。進捗率が高くても、難しい作業や統合テストが残っている可能性がある。

指標を読むときは、次を確認する。

- 分母と分子
- データの定義と取得方法
- 更新時点
- 欠測値や例外
- 指標を上げるための望ましくない行動
- 他の指標との整合性

### 6.2 予測と傾向

過去の実績から予測する場合、過去と未来の条件が同じとは限らない。予測値には、前提、信頼度、変動要因、更新タイミングを付ける。

遅延の予測では、単純な平均だけでなく、残作業の難易度、依存関係、要員の変化、レビュー待ちを確認する。

### 6.3 表計算から意思決定へ

表計算は集計のためだけでなく、仮説の検証に使う。数値を作った後に、どの判断を支援する資料なのかを明示する。

### 確認問題

1. 進捗率が高いのに危険なケースを挙げなさい。
2. 予測値に信頼度や前提を付ける理由を説明しなさい。
3. 指標が現場の望ましくない行動を誘発する例を挙げなさい。

## 第7章 情報セキュリティと職業倫理

### 7.1 リスクベースのセキュリティ

経験者には、規程を知っているだけでなく、業務上のリスクに応じて対策を設計することが求められる。アクセス権、委託先、ログ、データ保管、環境分離、バックアップ、復旧手順をプロジェクト計画へ組み込む。

### 7.2 重大インシデントと説明責任

インシデント時は、隠ぺい、憶測による発表、証拠の上書きを避ける。事実の確定を待ちすぎて報告が遅れることも避ける。暫定情報であることを明示し、更新時刻と次回報告時刻を設定する。

### 7.3 倫理的な意思決定

納期や売上の圧力があっても、品質記録の改ざん、問題の隠ぺい、特定者への不公平な機会配分を正当化してはいけない。判断に迷う場合は、個人で抱えず、上司、コンプライアンス、セキュリティ窓口へ相談する。

# 第2部 PM編

## 第8章 スコープ、WBS、スケジュール

### 8.1 スコープ境界を管理する

経験者が陥りやすいのは、過去の成功パターンを前提に、スコープの境界を早く固めすぎることである。要件の不確実性が高い場合は、確定部分、仮説部分、検証が必要な部分を分ける。

### 8.2 WBSを見積りと意思決定につなげる

WBSは作業一覧ではなく、計画と実績を比較する基準である。作業分解が粗すぎると遅延の兆候を捉えられず、細かすぎると更新コストが増える。

適切な粒度は、次の観点で決める。

- 担当を割り当てられるか
- 完了を客観的に判断できるか
- 期間や工数を見積もれるか
- 依存関係を把握できるか
- 進捗の変化を早期に検知できるか

### 8.3 スケジュールの回復

遅延回復には、要員追加だけでなく、スコープ分割、順序変更、並行化、品質リスクの受容、段階リリース、意思決定の前倒しなどがある。各案の副作用を比較し、回復策を実行した後の監視指標を決める。

### 確認問題

1. WBSの粒度が粗すぎる場合の問題を挙げなさい。
2. 遅延回復策を3つ挙げ、それぞれの副作用を説明しなさい。
3. 不確実な要件をスコープ管理へ組み込む方法を説明しなさい。

## 第9章 見積り、コスト、変更管理

### 9.1 見積りの品質

見積りの品質は、金額の近さだけでなく、前提と不確実性が明示され、更新可能であるかで評価する。過去実績を使う場合は、規模、技術、チーム、品質要求、期間の差を調整する。

### 9.2 予算と価値

予算差異を機械的にゼロへ戻すのではなく、追加費用がどの価値やリスク低減につながるかを説明する。逆に、予算内でも効果が得られないなら、計画の見直しが必要である。

### 9.3 変更の優先順位

すべての変更を同じように扱わない。法令対応、重大障害、顧客価値、セキュリティ、技術的負債、将来の運用費など、判断基準を合意する。

変更審査では、スコープ、納期、コスト、品質だけでなく、将来の運用負荷、アーキテクチャへの影響、他案件への波及を確認する。

### 確認問題

1. 見積りの品質を評価する観点を3つ挙げなさい。
2. 予算内でも計画を見直すべきケースを説明しなさい。
3. 変更要求の優先順位を決める評価基準を作りなさい。

## 第10章 リスク、課題、品質管理

### 10.1 リスク許容度

リスク対応は、リスクをゼロにする活動ではない。事業や顧客がどの程度のリスクを受け入れられるかを確認し、許容範囲を超える兆候を監視する。

### 10.2 重大課題の指揮

重大課題では、通常のタスク管理と危機対応を分ける。指揮者、情報収集担当、技術対応担当、利用者・経営向け広報担当を明確にし、意思決定のログを残す。

### 10.3 品質と技術的負債

技術的負債は、短期的な納期やコストと引き換えに、将来の変更・運用・障害対応の負荷を増やす。負債をすべてなくすのではなく、種類、影響、返済時期、放置コストを可視化して意思決定する。

### 確認問題

1. リスク許容度を確認すべき相手を挙げなさい。
2. 重大課題の指揮系統を通常のタスク管理と分ける理由を説明しなさい。
3. 技術的負債を経営層へ説明する方法を考えなさい。

## 第11章 チーム、顧客、ベンダーとの関係

### 11.1 権限委譲と自律性

経験者がチームを率いるとき、細かい指示で品質を安定させようとしすぎることがある。短期的には効率が上がっても、判断がPMに集中し、チームの自律性が失われる。

委譲では、結果、制約、判断権限、相談条件、レビュー時点を合意する。やり方をすべて指定するのではなく、目的と境界を明確にする。

### 11.2 ステークホルダー戦略

関係者ごとに、関心、影響力、期待、懸念、望ましい関与を整理する。重要なのは、全員を満足させることではなく、意思決定に必要な関係を維持することである。

### 11.3 ベンダーとのパートナーシップ

ベンダーを管理対象としてだけ扱うと、問題の早期共有が遅れる。一方で、友好的な関係を優先して契約や品質基準を曖昧にすると、責任分界が崩れる。

契約上の責任と協働上の関係を分け、早期警戒、エスカレーション、変更、検収のルールを明確にする。

### 確認問題

1. 委譲時に合意すべき「相談条件」の例を挙げなさい。
2. ステークホルダーを全員満足させることが現実的でない理由を説明しなさい。
3. ベンダーからの早期警戒を促す仕組みを提案しなさい。

---

## 第12章 リリース、重大障害、経営報告

### 12.1 リリースの意思決定

Go／No-Goは、成功確率だけでなく、失敗時の影響、切戻し可能性、代替運用、利用者への説明可能性で判断する。判定基準を満たさない場合は、例外承認の責任者と残存リスクを記録する。

### 12.2 重大障害の統制

障害時は、技術復旧と経営・顧客コミュニケーションを並行させる。原因が確定していなくても、影響、暫定対処、次回報告時刻を伝える。

復旧後は、個人のミスではなく、検知、判断、権限、手順、設計、教育のどこに改善余地があったかを確認する。

### 12.3 経営報告

経営報告は、事実の羅列ではなく、経営上の選択肢を提示する。報告には、推奨案、採用しない案、判断期限、判断しない場合の影響を含める。

# 第3部 PMO編

## 第13章 PMOの役割と責任分界

### 13.1 PMOの成熟度

PMOの成熟度は、会議や報告資料の数ではなく、組織の意思決定が改善したかで評価する。

- 支援型：PMが使えるテンプレート、相談、教育を提供する
- 管理型：標準、品質ゲート、報告、監査を運用する
- 指揮型：複雑案件や回復案件を直接統制する
- 戦略型：投資、ポートフォリオ、組織能力、人材育成を支援する

### 13.2 責任分界の設計

PMOが管理情報を集約しても、プロジェクトの成果責任が自動的にPMOへ移るわけではない。RACIだけでなく、意思決定権、承認権、情報提供義務、エスカレーション条件を定義する。

### 13.3 PMOの価値

PMOの価値は、次のような変化で示す。

- 問題の発見が早くなった
- 報告作成の負荷が減った
- 案件間の依存関係が見えるようになった
- 意思決定の滞留が減った
- 標準が実際に使われるようになった
- プロジェクト成功率や効果実現が向上した

### 確認問題

1. PMOの成熟度を測る指標を3つ提案しなさい。
2. PMOに責任が集中しすぎることで起きる問題を説明しなさい。
3. 自組織のPMOの価値を数値化する方法を考えなさい。

---

## 第14章 管理情報とデータ品質

### 14.1 管理情報モデル

経験者向けのPMOは、案件ごとの管理表を集めるだけでなく、組織共通の情報モデルを設計する。案件、成果物、課題、リスク、変更、依存関係、意思決定、効果を関連付ける。

### 14.2 データガバナンス

データには、定義、所有者、更新責任、参照権限、品質基準、履歴を設定する。ダッシュボードを作る前に、元データの定義と更新プロセスを整える。

### 14.3 データから示唆を出す

PMOの報告は、数値の集計から示唆へ進む必要がある。

- 何が変わったか
- なぜ変わった可能性があるか
- どの案件や組織へ波及するか
- 次に確認すべきことは何か
- どの判断が必要か

原因を断定できない段階では仮説として示し、追加確認の担当者と期限を置く。

### 確認問題

1. 情報モデルを設計するメリットを説明しなさい。
2. ダッシュボードの前にデータガバナンスが必要な理由を説明しなさい。
3. 数値から示唆を作るための問いを3つ挙げなさい。

---

## 第15章 会議体、標準化、品質ゲート

### 15.1 ガバナンスとしての会議体

会議体は、権限と情報の流れを設計するガバナンスである。誰が何を判断し、どの証拠を確認し、決定をどのように実行へ渡すかを定義する。

### 15.2 標準化と適応

標準は、すべての案件を同じにするためではなく、比較可能な最低限の情報と品質を確保するためにある。案件の特性による適応を認める場合は、適応理由と代替管理を記録する。

### 15.3 品質ゲートの実効性

品質ゲートが形骸化する理由は、基準が曖昧、判定者が不明、未達時の扱いがない、スケジュール優先で例外が記録されないことなどである。

ゲートを機能させるには、準備確認、レビュー、判定、例外承認、是正確認の流れを一貫させる。

### 確認問題

1. 会議体をガバナンスとして設計するとはどういうことか。
2. 標準への適応を認める場合に必要な記録を挙げなさい。
3. 品質ゲートが形骸化する原因と対策を説明しなさい。

---

## 第16章 KPI、ダッシュボード、予測

### 16.1 指標体系

指標は、事業効果、ポートフォリオ、プロジェクト、チーム、作業の階層で設計する。下位の活動指標が良くても、上位の効果指標が悪い場合がある。

### 16.2 先行指標と行動

先行指標を導入する場合は、閾値を超えたときの行動を決める。測るだけで対応が決まっていない指標は、報告負荷を増やすだけになる。

### 16.3 予測の信頼性

予測モデルや傾向分析を使う場合、データの偏り、母数、外部要因、定義変更を確認する。予測を真実として扱わず、意思決定を支援する仮説として扱う。

### 確認問題

1. 事業効果と作業指標が逆方向になる例を挙げなさい。
2. 閾値を超えたときの行動を定義する必要性を説明しなさい。
3. 予測の信頼性を下げる要因を挙げなさい。

---

## 第17章 ポートフォリオ、監査、ナレッジ

### 17.1 ポートフォリオの優先順位

案件の優先順位は、事業価値、戦略整合性、緊急度、規制、リスク、依存関係、実現可能性、機会費用で比較する。優先順位を変える場合は、何を後回しにしたかも記録する。

### 17.2 監査と学習

監査は、ルール違反を探すだけでなく、計画と実行のずれ、意思決定の質、組織的な障害を学ぶ機会である。指摘を是正して終わらせず、標準や教育へ反映する。

### 17.3 ナレッジを組織能力にする

ナレッジを組織能力に変えるには、事例を保存するだけでなく、判断基準、再利用条件、適用できない条件、成果を残す。成功事例だけでなく、失敗や中止の判断も価値がある。

### 確認問題

1. ポートフォリオ優先順位で機会費用を考慮する理由を説明しなさい。
2. 監査結果を組織学習へつなげる方法を挙げなさい。
3. 再利用条件をナレッジに記録する理由を説明しなさい。

---

## 第18章 PMOサービスと変革の定着

### 18.1 PMOサービスの設計

PMOサービスは、利用者の課題と意思決定を起点に設計する。サービスごとに、利用者、価値、入力、出力、提供頻度、品質指標、責任者、改善方法を定義する。

### 18.2 変革の実装

新しい標準、ツール、組織ルールは、合理的なだけでは定着しない。現場の負担、既存の評価制度、権限構造、習慣、導入の不安を扱う必要がある。

導入は、現状測定、仮説、試行、フィードバック、段階展開、効果確認の順で進める。利用率だけでなく、意思決定や品質が改善したかを確認する。

### 18.3 PM育成とコミュニティ

PMOは、研修を開催するだけでなく、案件レビュー、相談会、事例共有、メンタリングを組み合わせる。知識の標準化と、現場の判断力を両立させる。

### 確認問題

1. PMOサービスを設計するときの必須項目を挙げなさい。
2. 合理的な標準が定着しない原因を、組織面から説明しなさい。
3. PMコミュニティの効果を測る指標を提案しなさい。

# 第4部 実践演習

## 演習1：複数制約下の遅延回復

### 状況

大規模案件でテストが2週間遅れている。納期は固定、追加予算は限定的で、品質基準を下げることはできない。複数案件で同じ専門要員を必要としている。

### 課題

1. 遅延の根本原因と表面的な症状を分ける
2. スコープ、順序、要員、段階リリース、依存関係の選択肢を作る
3. 案件横断の影響を含む意思決定資料を作る
4. 推奨案、残存リスク、判断期限を明示する

## 演習2：戦略変更とポートフォリオ再評価

### 状況

年度途中で経営戦略が変更され、複数の案件の優先順位を見直すことになった。すでに投資した案件もあり、停止には現場の反発が予想される。

### 課題

1. 優先順位の評価基準を作る
2. 継続、縮小、延期、中止の条件を定義する
3. 機会費用と撤退コストを比較する
4. 関係者への説明と意思決定の記録方法を作る

## 演習3：KPIとダッシュボードの再設計

### 状況

経営向けダッシュボードは数値が多いが、問題の早期発見につながっていない。プロジェクトは進捗率を高く報告しているが、リリース後の障害が増えている。

### 課題

1. 現在の指標が誘発している行動を分析する
2. 先行指標と遅行指標を組み合わせる
3. PM向けと経営向けの表示を分ける
4. 閾値を超えた場合の行動と責任者を定義する

## 演習4：重大インシデントの経営対応

### 状況

リリース後に顧客データの一部が誤表示されている可能性が判明した。原因は未確定で、利用者影響の範囲も調査中である。SNSでの問い合わせも発生している。

### 課題

1. 最初の30分、2時間、24時間の対応計画を作る
2. 技術、法務、セキュリティ、顧客、経営の連絡体制を設計する
3. 事実、仮説、暫定対応、判断事項を分ける
4. 復旧後の調査と再発防止の責任分担を決める

## 演習5：PMOサービスの改革

### 状況

PMOは毎月報告資料を集めているが、PMから「入力負荷が高く、意思決定に役立たない」と言われている。経営層も案件の比較基準に不満を持っている。

### 課題

1. 利用者ごとの課題と期待価値を整理する
2. データ定義と入力負荷を見直す
3. 報告、レビュー、相談、監査のサービスを再設計する
4. 導入効果を測る指標と段階展開の計画を作る

# 第5部 学習の進め方と用語

## 19. 学習記録テンプレート

| 項目           | 記録内容                           |
| -------------- | ---------------------------------- |
| 対象案件・組織 | どの案件または組織で適用したか     |
| 判断テーマ     | 例：リリース延期の是非             |
| 目的・成功条件 | 何を実現し、何をもって成功とするか |
| 前提・制約     | 固定条件、可変条件、未確定事項     |
| 選択肢         | 比較した案と各案の影響             |
| 推奨案・判断者 | 推奨理由、決定者、決定日           |
| 実行結果       | 予定と実績、発生した差異           |
| 残存リスク     | 判断後も残った不確実性             |
| 学び           | 次回も再利用できる判断基準         |
| 標準への反映   | テンプレート、ルール、教育への反映 |
| 理解度         | レベル1～4                         |

## 20. 重要用語集

| 用語                   | 意味                                                           |
| ---------------------- | -------------------------------------------------------------- |
| アーキテクチャ         | システムの構造、構成要素、関係、設計原則                       |
| アーキテクチャ上の負債 | 短期判断の結果として将来の変更・運用負荷が増えた状態           |
| エグゼクティブ報告     | 経営層の判断に必要な影響、選択肢、推奨案を示す報告             |
| エスカレーション       | 権限や能力を超える問題を、判断可能な相手へ上げること           |
| 残存リスク             | 対応後も残るリスク                                             |
| ステークホルダー戦略   | 関係者の期待、影響、関与方法を設計すること                     |
| スコープ境界           | 実施範囲と対象外を分ける境界                                   |
| テクニカルデット       | 将来の変更・運用・障害対応の負荷となる技術的な未返済事項       |
| 品質ゲート             | 次の工程へ進めるかを確認する意思決定の節目                     |
| ポートフォリオ         | 戦略や投資の観点で横断管理する複数案件の集合                   |
| リスク許容度           | 組織や関係者が受け入れられるリスクの範囲                       |
| RACI                   | 実行、説明責任、相談、報告の役割を整理する方法                 |
| KPI                    | 目的達成の状況を測る重要業績指標                               |
| 先行指標               | 将来の結果を予測する兆候を表す指標                             |
| 遅行指標               | すでに起きた結果を表す指標                                     |
| データガバナンス       | データの定義、品質、権限、更新、責任を管理する仕組み           |
| PMOサービス            | PMOが利用者へ提供する支援、管理、判断支援の機能                |
| 例外承認               | 標準や品質基準から外れる判断を、権限者が記録付きで承認すること |
| 機会費用               | ある選択をしたことで失われる別の選択肢の価値                   |

## おわりに

経験者のPM・PMOには、過去の成功パターンを繰り返すだけでなく、状況に応じて前提を問い直す姿勢が求められる。

良い判断とは、常に正解を当てることではない。目的、制約、選択肢、リスク、判断者を明らかにし、適切なタイミングで決め、結果から学び、組織の次の判断を改善することである。
