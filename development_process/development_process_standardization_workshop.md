# 開発プロセス標準化ワーキング アジェンダ

## 1. ワーキングの目的

開発プロセス標準化ガイドをたたき台として、実際の案件で使える標準プロセスの最小形と、案件規模・リスクに応じた適用方法を合意する。

この場で完成版の規程を作り込むのではなく、次の事項を決めることを目的とする。

- 標準化するプロセスの範囲
- 小・中・大規模で必須とする活動・成果物
- 各プロセスの責任者、レビュー者、承認者
- 品質ゲートと次工程へ進む条件
- テンプレートを試行する対象案件と評価方法
- 未決事項、追加調査、次回までの宿題

## 4. 事前準備

### 4.1 参加者に依頼すること

- 直近案件を1件選び、実際に行った工程と成果物を一覧化する
- 「あってよかった活動」「負荷が高かった活動」「不足していた活動」を各3件挙げる
- 小・中・大規模の案件例を一つずつ想定する
- 現在使用しているテンプレート、台帳、チェックリストを持参する
- 標準化によって解決したい困りごとを一つ持参する

### 4.2 事務局が用意するもの

- 標準化ガイドの最新版
- 現行の設計書・プロジェクト計画書・テスト資料のサンプル
- 規模判定シートのたたき台
- プロセス定義シートのたたき台
- 決定事項・論点・アクションの記録欄
- オンライン参加者用の共有ボードまたは共同編集ファイル

## 6. セッション別の議論項目

### 6.1 開始・目的確認

#### 問い

- この標準化で、現在どの問題を最も解決したいか
- 「品質向上」「手戻り削減」「属人化解消」「説明責任」「教育」の優先順位は何か
- 標準化の対象は、社内開発、受託開発、保守改修のどこまでか
- 今回のワーキングで決めることと、決めないことは何か

#### 確認すること

- 標準化の目的を一文で表現できる
- 特定の開発モデルだけに依存していない
- 文書作成量の増加を成果としない

### 6.2 現状共有

#### 問い

- 案件ごとに進め方が変わり、問題が起きている工程はどこか
- 実施されているが証跡が残っていない活動は何か
- 文書はあるが、実際の判断や作業に使われていないものは何か
- 手戻り、不具合、遅延、認識違いはどの工程で発生しているか
- 現場が「標準化されると助かる」と考えるものは何か

#### 整理方法

| 区分       | 内容                         | 例                           |
| ---------- | ---------------------------- | ---------------------------- |
| 継続       | 現在のやり方を標準として残す | PRレビュー、テスト結果確認   |
| 改善       | 形式や責任を見直す           | レビュー記録、課題管理       |
| 廃止・統合 | 効果が低い、重複している     | 重複した報告書               |
| 新設       | 現在不足している             | リスク受容、テーラリング記録 |

### 6.3 標準化の境界

#### 議論するプロセス候補

- 案件開始・計画
- 要件定義・受入条件の合意
- 設計・アーキテクチャレビュー
- 実装・コードレビュー・構成管理
- テスト・不具合管理・品質判定
- リリース・移行・ロールバック
- 運用引き継ぎ・障害対応
- 変更・課題・リスク管理
- 終結・振り返り・改善

#### 問い

- 全案件で共通に必要なプロセスはどれか
- 案件規模ではなく、リスクによって必須にすべきプロセスはどれか
- 顧客や契約によって追加されるプロセスはどこで扱うか
- アジャイルの反復活動と、プロジェクト全体の管理活動をどう分けるか
- 標準の対象外とする活動を明確にできるか

### 6.4 規模・リスク判定

#### 決めること

- 小・中・大の基準となる条件
- 上位レベルへ引き上げるトリガー
- 規模判定を行う時期と承認者
- 判定を変更するタイミング
- 例外を認める条件と記録方法

#### 判定候補

| 観点           | 確認する質問                                           |
| -------------- | ------------------------------------------------------ |
| 体制           | チーム数、会社数、拠点数、関係者数はどの程度か         |
| 期間・規模     | 期間、工数、予算、リリース回数はどの程度か             |
| 影響範囲       | 変更が他システム、顧客、現場、業務に与える影響は何か   |
| 技術リスク     | 新技術、性能、可用性、移行、外部依存の不確実性はあるか |
| 情報管理       | 個人情報、機密情報、決済、監査対象を扱うか             |
| 運用影響       | 障害時の停止時間、復旧目標、業務影響はどの程度か       |
| 契約・顧客要求 | 成果物、承認、検収、監査、報告の指定があるか           |

#### 注意点

人数や期間だけで小規模と判定しない。小規模でも、重要業務、個人情報、外部連携、データ移行などがあれば上位レベルの管理を適用する。

### 6.5 プロセス定義

各プロセスについて、以下の表を使って確認する。

| 項目         | 議論する質問                           | 決定内容 |
| ------------ | -------------------------------------- | -------- |
| 目的         | 何を確定・保証するプロセスか           |          |
| 開始条件     | 何がそろえば着手できるか               |          |
| インプット   | 前工程から何を受け取るか               |          |
| 実施手順     | どの順序で作成、確認、修正、承認するか |          |
| アウトプット | 何を成果物・記録として残すか           |          |
| 完了条件     | 何を満たせば次へ進めるか               |          |
| 役割         | 作成、実施責任、レビュー、承認は誰か   |          |
| 品質確認     | どの観点・チェックで確認するか         |          |
| 証跡         | どこに、どの版で保存するか             |          |
| 変更時の扱い | 影響分析、再レビュー、再テストは必要か |          |
| 適用レベル   | 小・中・大のどこで必須か               |          |

#### 深掘りする問い

- 成果物がなくても、チケットやPRで代替できるものは何か
- 作成者とレビュー者を分ける必要があるか
- レビューを省略できる条件はあるか
- 完了条件を客観的に確認できるか
- そのプロセスを実施しない場合のリスクは何か

### 6.6 品質ゲート・役割

#### 問い

- どの時点で、誰が「進めてよい」と判断するか
- 成果物の存在だけでなく、内容の妥当性をどう確認するか
- 未解決不具合や未決事項を、どの条件で受容できるか
- 小規模案件でゲートを統合する場合、何を必ず残すか
- PM、開発、品質、運用、顧客の責任境界は明確か
- 判断できない場合のエスカレーション先は誰か

#### 最低限確認するゲート

- 要件確定
- 設計完了
- テスト完了
- リリース承認
- 運用引き継ぎ・案件終結

### 6.7 試行計画

#### 決めること

- 最初に試行する案件
- 試行するテンプレートと、試行しないテンプレート
- 試行期間、レビュータイミング、参加者
- 成功条件と中止・見直し条件
- 試行結果を標準へ反映する責任者

#### 評価する指標

| 評価観点   | 指標例                                 | 確認方法                   |
| ---------- | -------------------------------------- | -------------------------- |
| 使いやすさ | 記入時間、利用者の負担感、記入漏れ     | 利用者アンケート、作業時間 |
| 品質       | レビュー指摘、手戻り、不具合、要件漏れ | 案件記録との比較           |
| 進行       | 判断待ち、承認待ち、遅延タスク         | WBS、議事録、台帳          |
| 追跡性     | 要件と設計・テストの紐づき             | RTM、レビュー              |
| 運用性     | 引き継ぎ後の問い合わせ、障害対応時間   | 運用記録                   |

## 7. 議論のルール

- 個別案件の責任追及ではなく、再現可能な仕組みの改善を議論する
- 「必須」「条件付き」「推奨」「対象外」を使い分ける
- 意見、事実、決定事項を区別して記録する
- 結論が出ない場合は、未決事項、判断に必要な情報、期限、判断者を決める
- 文書を作ること自体を目的にしない
- 現場の負荷と、品質・説明責任・リスク低減の効果をセットで評価する
- 例外を禁止するのではなく、例外の条件と記録方法を標準化する

## 11. ワーキング終了時の成果物

最低限、次の状態になっていることを確認する。

- [ ] 標準化対象のプロセス一覧が決まっている
- [ ] 小・中・大の適用条件と、上位レベルへ引き上げる条件が決まっている
- [ ] 各プロセスの必須定義項目が決まっている
- [ ] 共通の必須成果物と、規模別の追加成果物が決まっている
- [ ] 品質ゲート、完了条件、承認者が決まっている
- [ ] テーラリングと例外の記録方法が決まっている
- [ ] 試行案件、試行期間、評価指標が決まっている
- [ ] 未決事項とアクションに担当・期限が設定されている

## 12. 次回ワーキングの候補

初回ワーキングで全プロセスを詳細化できない場合は、次回以降を次の順序で実施する。

1. 規模判定・テーラリングシートの確定
2. 計画、要件、設計プロセスの詳細化
3. レビュー・品質ゲート・変更管理の詳細化
4. テスト、リリース、運用引き継ぎの詳細化
5. 試行案件の振り返りと標準テンプレートの改訂
