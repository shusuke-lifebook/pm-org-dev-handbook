# 開発プロセス標準化 用語集

## 1. 目的

本用語集は、開発プロセス標準化ワーキングおよび関連資料で使用する用語の意味をそろえるためのものである。

案件や職種によって意味が変わりやすい用語は、この用語集の定義を基本とする。顧客、契約、法令、社内規程などに別の定義がある場合は、それらを優先し、案件固有の定義をプロジェクト計画書に記録する。

## 2. 使い方

- 資料では、同じ概念に複数の呼び方を使わない
- 略語を初めて使う場合は、正式名称または日本語を併記する
- 用語の意味が案件固有になる場合は、用語集を上書きせず、案件固有定義として記録する
- 新しい用語や意味の変更は、標準プロセスの改訂時に見直す

## 3. 標準化・案件管理

| 用語             | 英語・略語                                    | 定義・この資料での意味                                                                                                |
| ---------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 開発プロセス     | Development Process                           | 開発の目的を達成するために、活動、順序、役割、成果物、判定を定めた一連の仕組み。                                      |
| 標準プロセス     | Standard Process                              | 複数の案件で共通して利用できる、組織として定めた開発の進め方。                                                        |
| 適用レベル       | Application Level                             | 小・中・大など、案件の規模・リスクに応じて適用するプロセスの強度。                                                    |
| テーラリング     | Tailoring                                     | 標準プロセスを案件の特性に合わせ、活動や成果物を統合・簡略化・追加すること。                                          |
| 案件             | Project / Engagement                          | 目的、範囲、期限、体制を持つ開発・改修・導入・保守のまとまり。文脈に応じてプロジェクトとも呼ぶ。                      |
| 開発モデル       | Development Model                             | ウォーターフォール、アジャイル、ハイブリッドなど、開発活動の進め方。                                                  |
| ライフサイクル   | Lifecycle                                     | 企画、開始、計画、要件、設計、実装、テスト、リリース、運用、終結など、案件の全体的な流れ。                            |
| スコープ         | Scope                                         | 案件で実施する対象範囲。対象外も明示し、認識違いを防ぐ。                                                              |
| 成功基準         | Success Criteria                              | 案件の目的を達成したと判断する具体的な条件。納期や成果物の完成だけでなく、業務効果や品質を含める場合がある。          |
| ステークホルダー | Stakeholder                                   | 案件の成果、判断、実施、影響に関係する個人・組織。顧客、利用者、開発者、運用者、管理者など。                          |
| RACI             | Responsible, Accountable, Consulted, Informed | 作業の実行担当、最終責任者、相談先、共有先を整理する役割分担表。1つの作業に最終責任者を複数置かないことを基本とする。 |
| WBS              | Work Breakdown Structure                      | 案件の作業を成果物や作業単位に分解し、担当、工数、期限、依存関係を管理する構造。                                      |
| マイルストーン   | Milestone                                     | 重要な成果や判断の節目。期間を持つ作業ではなく、完了・承認・判定などの時点を表す。                                    |
| ベースライン     | Baseline                                      | 合意・承認され、以後の比較や変更管理の基準となる計画、要件、設計、構成などの状態。                                    |

## 4. プロセス・成果物・追跡

| 用語             | 英語・略語                         | 定義・この資料での意味                                                                                                     |
| ---------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| プロセス定義     | Process Definition                 | 目的、開始条件、入力、手順、出力、完了条件、役割、品質確認、証跡などを定めた定義。                                         |
| 成果物           | Deliverable                        | 案件の活動によって作成され、確認・共有・承認・引き継ぎの対象となる文書、コード、設定、データ、記録など。                   |
| インプット       | Input                              | あるプロセスを開始・実施するために必要な前工程の成果物、依頼、制約、情報。                                                 |
| アウトプット     | Output                             | プロセスの結果として作成・更新される成果物、記録、判断、チケットなど。                                                     |
| 完了条件         | Definition of Done / Exit Criteria | 作業や工程を完了し、次へ進めるために満たす具体的な条件。成果物が存在するだけでは完了としない。                             |
| 受入条件         | Acceptance Criteria                | 要件や機能が利用者・顧客の期待を満たしたと判断する条件。テストケースや受入判定の根拠にする。                               |
| トレーサビリティ | Traceability                       | 要求、設計、実装、テスト、受入の対応関係を追跡できる状態。                                                                 |
| RTM              | Requirements Traceability Matrix   | 要件と設計、実装、テスト、受入などの対応関係を表にしたもの。要件トレーサビリティ表。                                       |
| 証跡             | Evidence / Record                  | 実施、確認、判断、承認が行われたことを後から確認できる記録。議事録、レビュー記録、PR、CI結果、台帳など。                   |
| 版管理           | Version Control                    | 成果物や構成の変更履歴、現在の版、変更者、変更理由を管理すること。                                                         |
| 構成管理         | Configuration Management           | ソースコード、設計書、設定、DB変更、インフラ定義などの構成品目と、その組み合わせ・変更を管理すること。                     |
| テンプレート     | Template                           | 記載項目や構成をあらかじめ定め、案件間で再利用する雛形。必要な項目を埋めることが目的であり、形式だけを埋めるものではない。 |
| 台帳             | Register / Log                     | 課題、リスク、変更、不具合などを一覧で継続管理する記録。状態、担当、期限、判断を持たせる。                                 |

## 5. 品質・レビュー・判定

| 用語           | 英語・略語          | 定義・この資料での意味                                                                                   |
| -------------- | ------------------- | -------------------------------------------------------------------------------------------------------- |
| 品質管理       | Quality Control     | 成果物や作業結果を基準に照らして確認し、不備を検出・修正する活動。                                       |
| 品質保証       | Quality Assurance   | 品質が安定して作り込まれるよう、プロセスや仕組みの妥当性を確認・改善する活動。                           |
| レビュー       | Review              | 成果物や作業結果を複数の視点で確認し、問題、抜け、誤り、改善点を検出する活動。                           |
| ピアレビュー   | Peer Review         | 同等の専門性を持つ担当者が、成果物やコードを確認するレビュー。                                           |
| 独立レビュー   | Independent Review  | 作成担当と異なる組織・役割・立場の者が、客観性を重視して行うレビュー。大規模・高リスク案件で検討する。   |
| チェックリスト | Checklist           | 確認漏れを防ぐため、確認観点を項目化したもの。判断や専門家の確認を置き換えるものではない。               |
| 品質ゲート     | Quality Gate        | 工程の完了時に、品質、リスク、未解決事項、承認状況を確認し、次工程への移行可否を判断する場または条件。   |
| エントリー条件 | Entry Criteria      | プロセスや工程を開始してよい状態を示す条件。開始条件。                                                   |
| エグジット条件 | Exit Criteria       | プロセスや工程を完了して次へ進める状態を示す条件。完了条件。                                             |
| 不具合         | Defect / Bug        | 要件、設計、実装、期待動作などとの差異により、修正や判断が必要な状態。                                   |
| 重大度         | Severity            | 不具合が利用者、業務、データ、セキュリティなどに与える影響の大きさ。優先度とは別の概念。                 |
| リスク受容     | Risk Acceptance     | リスクを認識したうえで、追加対策を行わず、または残存リスクとして受け入れる判断。判断者と理由を記録する。 |
| Go/No-Go       | Go / No-Go Decision | リリース、移行、次工程への移行などを実施するか中止・延期するかの判断。                                   |
| 品質指標       | Quality Metric      | レビュー指摘、工程別不具合、テスト実施率など、品質や品質活動を評価する測定値。                           |

## 6. 要件・設計・テスト

| 用語           | 英語・略語                          | 定義・この資料での意味                                                                             |
| -------------- | ----------------------------------- | -------------------------------------------------------------------------------------------------- |
| 要件           | Requirement                         | 利用者、業務、顧客、法令、技術などから求められる条件や実現すべき内容。                             |
| 機能要件       | Functional Requirement              | システムが提供する機能、処理、画面、帳票、連携などの要件。                                         |
| 非機能要件     | Non-functional Requirement          | 性能、可用性、セキュリティ、保守性、拡張性、監査性、利用性など、機能以外の品質・制約に関する要件。 |
| 基本設計       | External Design / High-level Design | 要件を実現するため、利用者から見える機能やシステム間の外部仕様を定める設計。                       |
| 詳細設計       | Internal Design / Low-level Design  | 基本設計を実装可能な単位へ展開し、モジュール、処理、データ、例外などの内部仕様を定める設計。       |
| アーキテクチャ | Architecture                        | システムの主要な構成要素、関係、方式、技術上の原則を定めた全体構造。                               |
| ADR            | Architecture Decision Record        | アーキテクチャ上の重要な判断について、背景、選択肢、決定、結果を記録する文書。                     |
| テスト観点     | Test Perspective                    | テストで確認すべき切り口。正常、異常、境界、権限、性能、障害、運用など。                           |
| テストケース   | Test Case                           | 前提、入力、操作、期待結果、実績結果、判定を定義したテストの単位。                                 |
| テスト環境     | Test Environment                    | テストを実行するアプリケーション、サーバー、ネットワーク、データ、設定などの組み合わせ。           |
| テストデータ   | Test Data                           | テストに使用する入力データ、マスタ、ユーザー、異常・境界データなど。                               |
| 再テスト       | Retest                              | 不具合の修正後、同じ条件で修正結果を確認するテスト。                                               |
| 回帰テスト     | Regression Test                     | 変更によって既存機能に悪影響が出ていないことを確認するテスト。                                     |
| UAT            | User Acceptance Test                | 利用者または顧客が、業務目的と受入条件を満たすことを確認する受入テスト。                           |

## 7. リスク・課題・変更

| 用語             | 英語・略語                   | 定義・この資料での意味                                                                         |
| ---------------- | ---------------------------- | ---------------------------------------------------------------------------------------------- |
| 前提             | Assumption                   | 現時点では正しいものとして計画や判断に置く条件。崩れた場合の影響を確認する。                   |
| 制約             | Constraint                   | 予算、納期、技術、契約、法令、体制など、計画や設計の自由度を制限する条件。                     |
| リスク           | Risk                         | 将来発生する可能性があり、発生した場合に目的へ影響を与える不確実な事象。                       |
| リスク台帳       | Risk Register                | リスク、発生確率、影響、対策、担当、期限、状態、残存リスクを管理する一覧。                     |
| 課題             | Issue                        | すでに発生しており、解決や判断が必要な問題。                                                   |
| 課題台帳         | Issue Log                    | 課題の内容、影響、担当、期限、対応、判断、状態を管理する一覧。                                 |
| 未決事項         | Open Item / Pending Decision | 情報不足や判断待ちなどにより、まだ結論が出ていない事項。判断者と期限を置く。                   |
| 変更             | Change                       | 合意済みの要件、設計、計画、構成、運用などを変更すること。                                     |
| 変更管理         | Change Control               | 変更要求を受付、影響分析、承認、実施、確認、記録する一連の管理。                               |
| 影響分析         | Impact Analysis              | 変更が範囲、品質、納期、コスト、セキュリティ、運用などへ与える影響を調べること。               |
| エスカレーション | Escalation                   | 担当者やチームで解決できない課題・リスク・判断を、適切な責任者へ引き上げること。               |
| 手戻り           | Rework                       | 前工程の不備や変更などにより、完了した作業をやり直すこと。原因と影響を記録し、再発防止に使う。 |

## 8. リリース・運用・改善

| 用語               | 英語・略語                  | 定義・この資料での意味                                                                   |
| ------------------ | --------------------------- | ---------------------------------------------------------------------------------------- |
| リリース           | Release                     | ソフトウェアや設定を利用可能な環境へ提供すること。提供前後の確認を含めて扱う場合がある。 |
| 移行               | Migration                   | 既存環境・既存データ・既存業務から、新しい環境・データ・業務へ切り替える活動。           |
| ロールバック       | Rollback                    | 問題発生時に、変更前のバージョンや状態へ戻すこと。実行条件と手順を事前に定める。         |
| リリースリハーサル | Release Rehearsal / Dry Run | 本番リリースや移行の手順を事前に実行し、所要時間、抜け、復旧可否を確認すること。         |
| 運用引き継ぎ       | Operational Handover        | 開発チームから運用チームへ、監視、定常作業、障害対応、権限、連絡先などを移管する活動。   |
| Runbook            | Runbook                     | 定常運用、障害一次対応、復旧、確認などを手順化した運用手順書。                           |
| 監視               | Monitoring                  | システムの状態、性能、ログ、業務結果などを継続的に観測すること。                         |
| SLI                | Service Level Indicator     | サービスの状態や品質を測定する具体的な指標。可用性、応答時間など。                       |
| SLO                | Service Level Objective     | SLIについて、目標とする水準を定めたもの。                                                |
| SLA                | Service Level Agreement     | サービス提供者と利用者の間で合意したサービス水準や責任、対応条件。                       |
| インシデント       | Incident                    | サービスの中断、品質低下、セキュリティ事象など、通常状態からの望ましくない逸脱。         |
| ポストモーテム     | Postmortem                  | インシデントや重要な問題の事実、影響、原因、対応、再発防止を振り返る記録。               |
| 改善バックログ     | Improvement Backlog         | プロセス、品質、運用、技術的負債などの改善候補を優先度・担当・期限付きで管理する一覧。   |

## 9. アジャイル・反復開発

| 用語                   | 英語・略語      | 定義・この資料での意味                                                                                         |
| ---------------------- | --------------- | -------------------------------------------------------------------------------------------------------------- |
| アジャイル             | Agile           | 変化を前提に、短い反復とフィードバックを通じて価値を段階的に提供する開発の考え方・進め方。                     |
| スプリント             | Sprint          | 一定期間で計画、開発、確認を行う反復単位。名称や期間は採用する方法論により異なる。                             |
| バックログ             | Backlog         | 要求、機能、課題、改善など、今後実施する候補を優先順位付きで管理する一覧。                                     |
| プロダクトバックログ   | Product Backlog | プロダクトに必要な機能、改善、修正などを優先順位付きで管理する一覧。                                           |
| リファインメント       | Refinement      | バックログ項目の目的、範囲、受入条件、優先度、見積などを明確にする活動。                                       |
| デイリースタンドアップ | Daily Stand-up  | 短時間で進捗、次の作業、障害を共有する定例。報告のためだけでなく、障害解消につなげる。                         |
| レビュー・デモ         | Review / Demo   | 反復期間の成果を関係者に確認してもらい、フィードバックを得る活動。成果物の品質レビューとは区別する場合がある。 |
| レトロスペクティブ     | Retrospective   | 反復期間の進め方を振り返り、継続・改善・停止する活動を決める場。                                               |
| インクリメント         | Increment       | 反復の結果として追加され、利用可能な状態になった成果のまとまり。                                               |

## 10. 用語の使い分け

| 混同しやすい用語    | 使い分け                                                                                                                               |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| リスク / 課題       | まだ起きていない不確実な事象がリスク。すでに起きて対応が必要なものが課題。                                                             |
| 重大度 / 優先度     | 影響の大きさが重大度。対応する順番や緊急性が優先度。                                                                                   |
| 品質管理 / 品質保証 | 個別成果物の不備を検出・修正する活動が品質管理。プロセス全体を安定させる活動が品質保証。                                               |
| レビュー / 承認     | 内容を確認し意見・指摘を出すのがレビュー。責任者が正式に受け入れ、次へ進める判断をするのが承認。                                       |
| 成果物 / 証跡       | 作成・提供する対象が成果物。活動や判断を後から確認する記録が証跡。成果物が証跡を兼ねる場合もある。                                     |
| 完了条件 / 成功基準 | 工程や作業を終える条件が完了条件。案件の目的を達成したと判断する条件が成功基準。                                                       |
| テスト / レビュー   | 実行結果や動作を確認する活動がテスト。成果物や設計内容を人の視点で確認する活動がレビュー。                                             |
| 移行 / リリース     | データ・業務・環境を切り替える活動が移行。利用可能な版を提供する活動がリリース。                                                       |
| 標準化 / 統一       | 共通の目的・最低限のやり方・判断基準をそろえるのが標準化。すべてを同じ形式や手順にするのが統一。標準化は例外やテーラリングを許容する。 |
