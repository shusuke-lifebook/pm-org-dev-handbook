# 開発プロセス標準化ガイド

## 1. 目的

本ガイドは、大・中・小規模の開発案件で共通して利用できる開発プロセスの標準形と、案件規模に応じた適用方法を定めるものである。

設計書のフォーマットだけをそろえても、作成時期、レビュー、承認、変更管理、テスト、引き継ぎが案件ごとにばらばらでは品質を安定させられない。そのため、以下を標準化の対象とする。

- 何を、どの順序で実施するか
- 各工程で何をインプットとし、何を成果物として残すか
- 誰が作成・確認・承認するか
- どの条件を満たせば次工程へ進めるか
- 規模やリスクに応じて、どこまで簡略化・強化するか
- 実施結果をどの証跡で確認し、どう改善するか

## 2. 標準化の基本方針

### 2.1 プロセスは「成果物」ではなく「成果物を作り、確認し、合意する活動」として定義する

設計書、テスト結果、議事録などの成果物だけでなく、作成、レビュー、指摘対応、承認、版管理までを一連のプロセスとして扱う。

### 2.2 標準は一つ、適用レベルは複数とする

案件ごとに別のプロセスを作るのではなく、共通プロセスを定義し、規模・リスク・契約・顧客要求に応じて適用レベルを選択する。

### 2.3 文書を増やすのではなく、意思決定と追跡可能性を残す

独立した文書を増やすことが目的ではない。複数の内容を一つの計画書や台帳にまとめてもよいが、後から次を追跡できる状態を必須とする。

- 要求がどの設計・実装・テストに反映されたか
- 誰がいつ判断したか
- 未解決事項とリスクが何か
- 変更による影響が何か
- リリース後に何を引き継ぐか

### 2.4 テーラリングの判断を記録する

省略した成果物や簡略化したレビューがある場合は、「なぜ不要と判断したか」「代替する確認方法は何か」をプロジェクト計画またはテーラリング記録に残す。

## 3. 案件規模と適用レベル

規模は人数や予算だけでなく、変更の影響範囲、技術的不確実性、個人情報・セキュリティ、外部連携、停止時の業務影響、顧客・監査要求を合わせて判定する。

| 適用レベル | 想定する案件                                                   | 特徴                           | 最低限必要な管理                                                                       |
| ---------- | -------------------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------- |
| 小規模     | 小さな機能追加、短期改修、少人数、影響範囲が限定的             | 期間と関係者が少ない           | 目的・範囲、タスク、レビュー、テスト、リリース確認                                     |
| 中規模     | 複数チーム、複数機能、外部連携、数か月規模                     | 調整・依存関係・変更が増える   | 小規模の項目に加え、計画、リスク、要件追跡、品質計画、移行・運用準備                   |
| 大規模     | 多数の関係者、長期、複数システム、重要業務、監査・契約要求あり | 組織横断の意思決定と証跡が必要 | 中規模の項目に加え、段階ゲート、統合計画、構成管理、監査証跡、独立レビュー、リハーサル |

### 3.1 規模判定チェック

次のいずれかに該当する場合は、単純な小規模案件として扱わず、一段上の適用レベルを検討する。

- 複数の開発チームまたは外部ベンダーが関与する
- 他システム、データ、API、ネットワーク、現場機器と連携する
- 個人情報、機密情報、決済、法令・監査対象を扱う
- 障害時の業務影響が大きい、または停止が許容されない
- 新技術、未経験の方式、性能・可用性などの不確実性が高い
- データ移行、段階リリース、並行稼働が必要である
- 顧客から成果物、承認、検収、監査証跡を求められている

## 4. プロセス定義書に持たせる項目

各プロセスは、次の項目を持つ1枚の定義として管理する。これが標準化の中心フォーマットである。

| 項目               | 記載内容                                         |
| ------------------ | ------------------------------------------------ |
| プロセスID・名称   | 例：REQ-01 要件定義、TST-02 結合テスト           |
| 目的               | この活動で何を確定・保証するか                   |
| 適用条件           | どの案件、工程、変更に適用するか                 |
| 適用レベル         | 小・中・大の必須、条件付き、推奨の区分           |
| 開始条件           | 着手できる前提、承認、入力の準備状況             |
| インプット         | 前工程の成果物、依頼、制約、既知課題             |
| 実施手順           | 作成、確認、レビュー、修正、承認の流れ           |
| 判断・承認ポイント | 合意事項、判定基準、エスカレーション条件         |
| アウトプット       | 成果物、更新台帳、記録、チケット                 |
| 完了条件           | 次工程へ進めるための具体的な条件                 |
| 役割               | 作成者、実施責任者、レビュー者、承認者           |
| 品質確認           | チェックリスト、レビュー観点、自動検査           |
| 証跡               | 保存場所、ファイル名、版、承認記録、チケット番号 |
| 変更時の扱い       | 変更申請、影響分析、再レビュー、再テスト         |
| 指標               | 進捗、品質、コスト、リスク、作業効率の測定方法   |
| テーラリング       | 省略・統合・強化できる項目と判断理由             |
| 関連プロセス       | 前後工程、依存する規約、関連テンプレート         |

## 5. 標準ライフサイクル

開発モデルがウォーターフォール、アジャイル、ハイブリッドのいずれであっても、次の能力を持つ活動を漏れなく配置する。アジャイルでは工程をスプリントやリリース単位に繰り返し適用する。

| 区分           | 主なプロセス                                            | 代表的な成果物                                                |
| -------------- | ------------------------------------------------------- | ------------------------------------------------------------- |
| 企画・提案     | 目的、効果、実現性、概算、初期リスクの確認              | 企画書、提案書、概算見積、初期リスク一覧                      |
| 開始           | 目的、範囲、体制、責任、成功基準の合意                  | プロジェクト憲章、SOW、体制図、RACI、キックオフ資料           |
| 計画           | WBS、スケジュール、予算、品質、リスク、連絡方法の定義   | プロジェクト計画書、WBS、マイルストーン、品質計画、リスク台帳 |
| 要件           | 業務・機能・非機能・受入条件の確定                      | 要件定義書、業務フロー、非機能要件、RTM、要件レビュー記録     |
| 設計           | 方式、画面、API、データ、処理、セキュリティ、運用の設計 | 基本設計書、詳細設計書、API仕様、ER図、運用設計書             |
| 実装           | コーディング、構成管理、静的解析、コードレビュー        | ソースコード、レビュー記録、ビルド定義、SBOM                  |
| テスト         | テスト計画、ケース作成、実行、不具合管理、品質判定      | テスト計画、仕様書、結果報告、不具合台帳、品質評価            |
| 移行・リリース | 移行、リリース、ロールバック、利用者通知、判定          | リリース計画、移行計画、リハーサル報告、Go/No-Go記録          |
| 運用・保守     | 監視、障害対応、変更、問い合わせ、改善                  | Runbook、監視設計、SLA/SLO、インシデント報告、改善バックログ  |
| 終結・振り返り | 検収、契約上の完了、ナレッジ化、改善                    | 検収記録、完了報告、振り返り記録、教訓一覧                    |

## 6. 規模別の作成物と実施レベル

### 6.1 共通の必須最小セット

規模にかかわらず、次の内容は省略しない。文書を分けず、チケット、PR、議事録、既存の設計書に統合してもよい。

- 目的、対象範囲、対象外、成功基準
- 担当者、レビュー者、承認者
- タスク、期限、依存関係
- 要求または変更内容と受入条件
- 設計・実装のレビュー記録
- テスト観点、実施結果、未解決不具合
- リリース手順、戻し方、実施結果
- 未決事項、リスク、意思決定の記録

### 6.2 規模別マトリクス

| 管理領域 | 小規模                               | 中規模                             | 大規模                                                 |
| -------- | ------------------------------------ | ---------------------------------- | ------------------------------------------------------ |
| 案件定義 | 1ページ程度の目的・範囲・成功基準    | プロジェクト憲章または計画書       | 憲章、SOW、契約・検収条件、段階計画                    |
| 計画     | タスク一覧と期限                     | WBS、工程表、体制、定例            | 統合WBS、複数チーム計画、進捗・予算統制                |
| 要件     | 要求一覧と受入条件                   | 要件定義書、業務フロー、RTM        | 要求管理プロセス、変更審査、承認ベースライン           |
| 設計     | 変更箇所の設計メモまたは設計書更新   | 基本・詳細設計、IF・データ設計     | アーキテクチャ審査、設計標準、横断設計、独立レビュー   |
| 品質     | 作成者以外のレビュー、テスト結果確認 | 品質計画、工程別レビュー、品質指標 | 品質保証計画、監査、第三者・専門家レビュー、品質ゲート |
| リスク   | 重要リスクを一覧化                   | リスク台帳、課題台帳、定期見直し   | 定量評価、予備費・代替策、経営エスカレーション         |
| 構成管理 | Git、PR、版の識別                    | ブランチ・リリース・環境の管理     | 構成品目、ベースライン、変更管理委員会、監査証跡       |
| テスト   | 単体・影響範囲の確認                 | 結合・総合・受入の計画と結果       | 性能、障害、セキュリティ、移行、現場実証、リハーサル   |
| リリース | 手順、確認、ロールバック             | リリース判定、移行計画、利用者通知 | Go/No-Go会議、段階展開、切替統制、復旧訓練             |
| 運用     | 連絡先、障害時の対応                 | Runbook、監視、引き継ぎ            | SLA/SLO、監査、BCP/DR、運用受入、改善サイクル          |
| 終結     | 作業完了と残課題の確認               | 検収、振り返り、引き継ぎ完了       | 契約完了、監査証跡整理、資産・知見の組織還元           |

## 7. 工程ごとの標準プロセス項目

### 7.1 開始・計画

- 目的、背景、対象範囲、対象外、成功基準を合意する
- ステークホルダー、意思決定者、実行責任者を定める
- WBSを作成し、成果物、担当、工数、期限、依存関係を明確にする
- 前提、制約、リスク、未決事項を初期登録する
- 定例会、報告、エスカレーション、議事録のルールを決める
- 品質基準、レビュー方式、承認方法、証跡の保存先を定める

**完了条件**: 目的・範囲・体制・計画・主要リスクについて、必要な責任者が合意している。

### 7.2 要件定義

- 業務上の課題と達成したい効果を確認する
- 機能要件、非機能要件、制約、対象外を整理する
- 業務フロー、ユースケース、画面・帳票・外部連携の対象を整理する
- 受入条件を要求ごとに定義する
- 要求IDを付与し、設計・実装・テストへ追跡できるようにする
- 未確定事項を放置せず、期限と判断者を決める

**完了条件**: 要求の優先度、受入条件、対象範囲、未決事項の扱いが合意されている。

### 7.3 設計

- 要件、既存システム、標準アーキテクチャ、運用制約をインプットとする
- 方式、データ、画面、API、バッチ、エラー、セキュリティ、ログ、運用を必要な範囲で設計する
- 正常系だけでなく、異常系、境界値、障害時、再実行、権限を確認する
- 要件IDとの対応を記録する
- 設計レビューで指摘を管理し、修正後に再確認する

**完了条件**: 実装者とテスト担当者が設計意図を理解でき、主要なリスクと未決事項が管理されている。

### 7.4 実装・構成管理

- コーディング規約、ブランチ運用、PR、CI、静的解析のルールを適用する
- 変更単位を小さくし、目的、影響範囲、テスト結果をPRに記録する
- コード、設定、DB変更、インフラ定義を追跡可能な形で管理する
- 依存ライブラリ、ライセンス、脆弱性を確認する
- レビュー指摘の対応と再レビューを完了させる

**完了条件**: 必須チェックを通過し、レビュー承認済みで、対象環境へ再現可能な状態になっている。

### 7.5 テスト・品質管理

- テスト計画で対象、範囲、観点、体制、環境、データ、合格基準を定める
- 要件・設計から正常、異常、境界、権限、性能、障害、運用の観点を導出する
- 不具合は重大度、再現条件、原因、対応、再テスト結果を管理する
- 結果だけでなく、未実施、除外、既知課題とリスク受容を記録する
- 工程ごとの品質ゲートで、次工程へ進めるかを判断する

**完了条件**: 合格基準を満たし、残存不具合とリスクの受容者が明確になっている。

### 7.6 リリース・移行・運用引き継ぎ

- リリース対象、手順、所要時間、確認項目、連絡先、ロールバック条件を定める
- データ移行がある場合は、件数・整合性・バックアップ・リハーサルを確認する
- 監視、ログ、アラート、権限、問い合わせ、障害一次対応を準備する
- Go/No-Goの判定材料をそろえ、責任者が判断する
- リリース後の確認期間と、問題発生時の体制を明確にする

**完了条件**: リリースの承認、運用受入、利用者通知、ロールバック準備が完了している。

### 7.7 終結・改善

- 検収、残課題、未完了作業、契約上の完了条件を確認する
- 目標、品質、納期、コスト、リスク、作業効率を振り返る
- 問題の個人責任ではなく、プロセス・仕組み・前提の観点で原因を分析する
- 再発防止策を担当・期限付きで改善バックログへ登録する
- テンプレート、チェックリスト、見積・実績データを更新する

**完了条件**: 成果物と証跡が保管され、残課題の所有者が決まり、改善事項が次の案件で利用可能になっている。

## 8. 品質ゲート

工程の完了は、成果物の存在ではなく、判定条件を満たしていることで確認する。

| ゲート          | 判定すること                                             | 主な証跡                           |
| --------------- | -------------------------------------------------------- | ---------------------------------- |
| G0 開始承認     | 目的、範囲、体制、契約・前提が妥当か                     | 憲章、計画、承認記録               |
| G1 要件確定     | 要求、優先度、受入条件、未決事項が管理されているか       | 要件定義書、RTM、レビュー記録      |
| G2 設計完了     | 実装・テストに必要な設計と横断観点がそろっているか       | 設計書、レビュー記録、指摘管理票   |
| G3 実装完了     | コードレビュー、ビルド、静的解析、単体テストが完了したか | PR、CI結果、テスト結果             |
| G4 テスト完了   | 合格基準、残存不具合、リスク受容が妥当か                 | テスト結果、品質評価、不具合台帳   |
| G5 リリース承認 | 移行・運用・復旧準備とGo/No-Go判断が完了したか           | リリース計画、リハーサル、判定記録 |
| G6 終結承認     | 検収、引き継ぎ、残課題、振り返りが完了したか             | 完了報告、引継ぎ記録、改善事項     |

小規模案件では、複数ゲートを一つのチェックに統合してよい。ただし、要件、品質、リリースの判定を省略してはならない。

## 9. 共通台帳・テンプレートとして作成するもの

最初に作成すべき標準テンプレートは、次の順序とする。

1. **プロジェクト計画書**: 目的、範囲、体制、WBS、スケジュール、品質、リスク、コミュニケーション
2. **要件定義書・要件トレーサビリティ表**: 要求、受入条件、設計・テストとの対応
3. **設計書テンプレート**: 方式、画面、API、データ、処理、エラー、セキュリティ、運用
4. **レビュー記録・チェックリスト**: 対象、観点、指摘、対応、再確認、承認
5. **課題・リスク・変更管理台帳**: 内容、影響、優先度、対応者、期限、判断、状態
6. **テスト計画・結果・不具合台帳**: 観点、ケース、結果、証跡、残存リスク
7. **リリース・移行・ロールバック計画**: 手順、判定、連絡、復旧、実績
8. **運用引き継ぎ・Runbook**: 定常作業、監視、障害、問い合わせ、権限、連絡先
9. **完了報告・振り返りテンプレート**: 実績、品質、課題、教訓、改善
10. **テーラリング記録**: 適用レベル、採用・省略項目、判断理由、承認者

## 10. 指標と確認方法

指標は評価のためだけでなく、プロセスを改善するために使う。案件規模に応じて必要なものだけを選ぶ。

| 分類   | 指標例                                       | 確認すること                           |
| ------ | -------------------------------------------- | -------------------------------------- |
| 進捗   | マイルストーン達成率、遅延タスク数           | 計画と実績の差、早期の遅延兆候         |
| 品質   | レビュー指摘数、テスト不具合数、工程別流出数 | 早期検出、レビュー観点、再発傾向       |
| 要件   | 要件変更数、未追跡要件数、RTM充足率          | 要求の安定性と追跡可能性               |
| リスク | 高リスク残数、期限超過リスク数               | 対策の実効性、エスカレーションの適時性 |
| テスト | ケース実施率、合格率、再テスト滞留           | 出荷判断の妥当性                       |
| 運用   | 障害件数、復旧時間、問い合わせ件数           | 運用設計と引き継ぎの不足               |
| 効率   | 見積工数と実績工数、手戻り工数、自動化率     | 見積・プロセス・自動化の改善           |

数値目標を設定する場合は、案件特性、測定方法、データの解釈、目標未達時の対応まで定義する。単純に指摘数や不具合数を減らすことだけを目標にしない。

## 11. 標準化の導入手順

1. 現行案件から、工程、成果物、会議、レビュー、台帳、承認を棚卸しする
2. 共通している活動と、案件固有の活動を分ける
3. 本ガイドのプロセス定義項目で、最小限の標準プロセスを作る
4. 小・中・大の3段階で、必須・条件付き・推奨を決める
5. 1案件で試行し、作成負荷、抜け漏れ、意思決定速度、品質への効果を確認する
6. 実績データと利用者の意見を反映してテンプレートを改訂する
7. 標準プロセスのオーナー、改訂周期、版管理、教育方法を決める

## 12. 運用ルール

- 標準テンプレートには版、適用開始日、オーナー、改訂履歴を持たせる
- プロジェクト開始時に適用レベルとテーラリングを承認する
- 重要な判断、変更、リスク受容、Go/No-Goは必ず証跡を残す
- テンプレートの利用率だけでなく、手戻り削減や品質改善の効果を確認する
- 案件終了時に、標準へ戻すべき改善をバックログ化する
- 法令、顧客標準、セキュリティ基準、契約条件がある場合は、それらを優先する

## 13. 最初に作るべき標準セット

導入初期にすべてを作り込むのではなく、次の7点から始める。

- 規模判定・テーラリングシート
- プロジェクト計画書
- 要件・受入条件・RTM
- レビュー記録と工程別チェックリスト
- 課題・リスク・変更台帳
- テスト計画・結果・不具合台帳
- リリース・運用引き継ぎ・完了報告

この7点で、計画、要求、設計、品質、変更、リリース、改善の主要な管理点を一通りカバーできる。案件で実際に使い、負荷と効果を測ったうえで、必要な専門テンプレートを追加する。
